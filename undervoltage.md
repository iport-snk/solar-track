## 2. Может ли недостаток напряжения приводить к зависанию USB IMU?

**Да, именно это и происходит.** Механизм сбоя:

1. **Просадка питания 5V на Raspberry Pi**:
   - Флаг `Undervoltage detected` срабатывает на Raspberry Pi, когда входное напряжение 5В падает ниже порога **4.63 В**.
   - При срабатывании реле и пуске моторов (inrush current) индуктивная нагрузка вызывает резкий кратковременный импульс тока и просадку напряжения.

2. **Влияние на шину USB и контроллер CP2102 (`/dev/ttyUSB0`)**:
   - Питание портов USB (линия VBUS 5V) падает синхронно с питанием Raspberry Pi.
   - Мост USB-UART **Silicon Labs CP2102** запитывается от USB. Внутри него стоит собственный LDO-стабилизатор 3.3В. При падении входного напряжения 5В до 4.5В и ниже, а также при высокочастотных бросках, чип CP2102 испытывает **Brownout Reset** (сброс по питанию) либо сбой в буфере FIFO конечной точки USB.
   - Также сам датчик IMU (если питается от шины USB через CP2102) кратковременно перезагружается или сбивается его тактовый генератор UART.

3. **Сбой высокоскоростной передачи на 921600 бод**:
   - Скорость передачи данных IMU составляет **921600 бод** (1 байт передается всего за ~10.8 микросекунд).
   - Даже микросекундная помеха по питанию приводит к потере нескольких байт или битовым ошибкам (Framing Error / Parity Error / Noise Error) на стороне драйвера ядра `cp210x`.

## 3. Почему в софте это проявляется как «зависшее старое значение»?

В коде `include/ImuController.hpp` есть несколько критических уязвимостей, из-за которых софт **никогда не может восстановиться после первого же сбоя питания**:

### А. Рассинхронизация бинарного потока из-за потери байт
- Пакет IMU имеет фиксированный формат:
  `[0xFC (STF)] [0x41 (Type AHRS)] [0x30 (Len=48)] [SN] [CRC8] [CRC16_L] [CRC16_H] [Payload 48 байт] [0xFD (END)]` (всего 56 байт).
- В `ImuController.hpp`:
  ```cpp
  if (byte == STF) {
      read(fd, header, 6);
      ProcessPaket(static_cast<PacketType>(header[0]));
  }
  ```
  В POSIX Linux при `VMIN=1` вызов `read(fd, buf, 6)` **не ждет 6 байт** — он возвращает столько, сколько уже пришло в буфер ядра (например, 2 или 3 байта).
  Аналогично `read(fd, &ahrs, sizeof(ahrs))` читает неполный пакет.
- Если из-за Undervoltage потерялся хотя бы один байт, парсер навсегда теряет границы пакета. Байт `0xFC` часто встречается **внутри чисел float** или CRC (в реальном пакете байт 5 равен `0xFC`!).
- Парсер принимает случайный `0xFC` из середины пакета за старт нового фрейма, читает со смещением, тип пакета не совпадает, пакет отбрасывается.
- **Новые валидные пакеты больше не парсятся**, а значение `ahrs.roll` остается тем, каким оно было до сбоя.

### Б. Зависание (Deadlock) или 100% CPU при сбросе дескриптора порта
- Если при сильной просадке USB-устройство на долю секунды отвалилось от шины:
  - Вызов `read()` начинает возвращать `0` (EOF) или `-1` (EIO).
  - В коде написано:
    ```cpp
    ssize_t bytes_read = read(fd, &byte, 1);
    if (bytes_read <= 0) {
        if (!running_.load()) break;
        continue;
    }
    ```
  - Происходит бесконечный цикл `continue` на 100% загрузки одного ядра CPU.
  - Дескриптор `fd` уже недействителен, а попытки переоткрыть порт (`close` + `open`) в коде нет вообще.
- Кроме того, `read(fd, &ahrs, sizeof(ahrs))` вызывается **под захваченным `ahrsMutex`**. Если чтение заблокировалось, любой вызов `CMD::poz()` -> `ImuController::getRoll()` блокируется на мьютексе навсегда.

### В. Отсутствие таймаута устаревания данных (Watchdog)
- В `ImuController` нет отслеживания времени последнего успешного пакета.
- Переменная `ahrs` хранит последние записанные байты. Даже если связь с IMU оборвалась 3 недели назад, `getRoll()` возвращает то самое старое значение, не сообщая об ошибке.

## 4. Рекомендации по аппаратному устранению (Hardware)

1. **Разделение питания (Критично)**:
   - Не питать Raspberry Pi от той же линии 5В/12В, от которой питаются силовые реле и моторы актуаторов, без качественной развязки.
   - Использовать для Raspberry Pi отдельный стабилизированный блок питания 5V / 3A-5A (официальный блок питания RPi или качественный DC-DC преобразователь с запасом по току).
2. **Фильтрация индуктивных выбросов на моторах и реле**:
   - Параллельно контактам моторов установить снабберные RC-цепи или варисторы.
   - Параллельно катушкам реле должны стоять обратно включенные диоды (flyback diodes, например 1N4007), гасящие выбросы самоиндукции при размыкании.
3. **Электролитические конденсаторы большой емкости**:
   - Установить электролитический конденсатор (1000–4700 мкФ) на входе питания 12В/24В перед драйверами моторов для компенсации пусковых токов.
4. **USB ферритовые фильтры и экранирование**:
   - Установить ферритовые кольца/клипсы на USB-кабель IMU.

## 5. Рекомендации по программному устранению (Software)

Программная часть должна быть устойчива к любым сбоям оборудования:

1. **Автоматическое переподключение (Auto-reconnect)**:
   - Если `read()` вернул `<= 0` или данные не поступают более 2 секунд: закрыть `fd`, подождать 500 мс и заново открыть `/dev/ttyUSB0` с инициализацией termios.
2. **Полноценный конечный автомат сборки фреймов (State Machine)**:
   - Буферизация байт: читать в кольцевой/линейный буфер.
   - Искать `STF (0xFC)`.
   - Проверять полную длину пакета (`len + 8` байт), байт `END (0xFD)`.
   - Проверять контрольные суммы (`crc8` для заголовка, `crc16` для данных).
   - При несовпадении CRC — сдвигать буфер на 1 байт и продолжать поиск, а не «зависать».
3. **Вынос чтения из-под мьютекса**:
   - Читать и валидировать пакет в локальный буфер.
   - Захватывать `ahrsMutex` только на пару наносекунд для копирования уже проверенной структуры `ahrs`.
4. **Сторожевой таймер данных (Data Freshness Watchdog)**:
   - Запоминать `std::chrono::steady_clock::now()` при каждом успешном пакете.
   - Если данные не обновлялись > 1.0 сек, `getRoll()` должен возвращать флаг ошибки или `std::nullopt` / `NaN`, чтобы система знала, что датчик отвалился, а не пыталась рулить по «замороженным» показаниям.
